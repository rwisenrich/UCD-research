# 01 — Discovery Loop

The Algorithms-of-Reality engine treats discovery as a controlled recursive process rather than a one-shot fit.

## Canonical loop

$$
\boxed{
\text{intake}
\rightarrow
\text{route pressure}
\rightarrow
\text{candidate generation}
\rightarrow
\text{null/control tournament}
\rightarrow
\text{retest}
\rightarrow
\text{theorem/rule ledger}
\rightarrow
\text{Living Tree artifact}
}
$$

Each cycle must retain:

1. the source object being attacked;
2. the candidate transformation/operator/law;
3. the exact test or falsification predicate;
4. the control/null comparison;
5. the result certificate;
6. the branch status after the test;
7. the next dependency revealed by success or failure.

## Route-pressure principle

When many downstream results depend on one unresolved object, that object receives higher search priority. This is the operational form of the Dependency Funnel and Bottleneck Compression rules.

If a branch has dependencies

$$
B_1,\dots,B_n
$$

requiring unresolved object `X`, its route pressure is treated as a priority weight increasing with the downstream dependency count, while still being constrained by testability and source provenance.

## Retest before promotion

Internal closure is not theorem closure. A candidate generated by a recursive engine remains provisional until it survives:

- a fresh rerun;
- independent verification where available;
- held-out or alternate-condition testing;
- null/control separation;
- duplicate-evidence audit;
- source/provenance reconciliation.

A failed candidate is not deleted. Its branch becomes evidence about which route does not carry the target structure.

## Artifact persistence

Scheduled recursion appends rather than replaces prior reports, result objects, failures, and repairs. This lets later work reconstruct the actual sequence of discovery rather than only the final branch state.
